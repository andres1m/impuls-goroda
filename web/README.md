# Impuls Goroda Mini App

Run `npm ci` and `npm run dev` from `web/`. For local development, copy `public/config.example.json` to `public/config.json` and set `apiBaseUrl` to the gateway origin. Local HTTP is accepted only for localhost.

Set the optional public `botUsername` in runtime config to show a bot link when the owner has no route or scenario. Send `/start` in the bot to choose a theme. Configure the bot webhook at `/api/v1/max/webhook` and register its commands with MAX; deploying the app alone does not register them.

`npm run build` writes the static site to `web/dist`. The public HTTPS service in Compose serves that directory at `https://impulsgoroda.duckdns.org/` and provides `/config.json` with the same origin as the API. Local `public/config.json` and `docker/caddy/config.json` are ignored by git. Runtime config contains only the public API origin, the mode flag and an optional browser map key restricted to that origin.

When `/config.json` contains `"prototypeMode": true`, the Mini App opens a clearly labeled synthetic route workspace. The MAX `startapp` payload selects a demo scenario; browser preview also accepts `?demo=vibe`. The three sample themes switch immediately. Rebuild offers a different local sample route within the selected theme and applies it only after review; it does not query the database. The workspace also includes manual start and finish, lunch, a conditional Pushkin Card mode, and local-only actions. Set `twoGisApiKey` in the runtime config to display the 2GIS map, geocode stops, and search nearby cafes. The gateway uses `TWO_GIS_API_KEY` to request route geometry. Without a key or when the map fails, the schedule remains available. Example route times and visits are not verified navigation, booking, or persistent server routes.

Lunch searches request the user's current location on each opening, then query real 2GIS cafes within the selected radius. Markers search falls back to Places search; an error never supplies invented cafes. Multiple lunch stops can be added, moved after a visit, or deleted independently. Choosing a cafe immediately inserts it into the local route and requests a walking path from the current location. Multiple lunch windows require schedule recalculation. Location used for the walking path stays in memory. Completed visits are marked green only after an explicit user action. Start and finish can be selected on the map. Pushkin Card settings never ask for a remaining balance.

With prototype mode disabled, the Mini App authenticates MAX launch data through Gateway and restores the user's context. A bot scenario opens the conditions editor, including start/finish selection on the 2GIS map, draft saving and explicit review of extracted conditions. Calculation returns server route variants or an explained refusal. Owner routes support selection, saving, execution marks with explicit actual times, pin/removal/Panic proposals, explicit apply/reject and share link creation/revocation. Shared links open a separate read-only screen without owner authentication. Route geometry and transition evidence come from the server; the map does not turn estimated travel into verified travel.

Product lunch search runs through the owner-only Gateway endpoint around fresh device geolocation. The lunch interval and the lunch button open the same search screen. Results contain real provider place names/coordinates and straight-line distance; hours, prices and availability remain unknown. Walking navigation opens externally in 2GIS. Adding, moving or deleting multiple lunches in the saved plan is not connected yet. Copying shared routes, automatic catalog cancellation notifications and the complete bot clarification dialog also remain incomplete. Browser prototype actions do not imply these server features are available.

For a product release, explicitly combine `compose.yaml` with `compose.product.yaml`. Set `RELEASE_TAG`, `SOURCE_REVISION`, `WEB_DIST_DIR` and `WEB_RUNTIME_CONFIG` in the ignored `.env`. Copy `docker/caddy/config.product.example.json` to the ignored runtime config file and set the browser map key there; keep bot tokens, database passwords and AI keys out of that JSON. Gateway's server-side `TWO_GIS_API_KEY` remains in `.env`. The overlay passes optional AI keys to Gateway and uses release-specific service image tags; labels record the supplied revision but do not verify image contents.

Build the frontend and the Gateway/optimizer/syncer images from the same source checkout before deployment. Missing bind paths are rejected instead of silently creating empty folders. Relative paths resolve from the first Compose file. Keep the current Compose project name, persistent volumes and Caddy certificate storage when replacing an existing stand; record the previous source, image tags and runtime config for rollback. The `public` profile is required for Caddy. Caddy serves the static build and TLS, while Nginx remains the internal API proxy. Do not run a second bot consumer with the same token or delete volumes during the switch. This configuration does not populate the catalog, prepare routing graphs or prove MAX/API/provider readiness.

`npm test` provides checks for runtime configuration, session exchange, route loading, and UI states. Recent product and prototype changes have not been tested; existing interaction expectations may need updating. Successful local builds do not establish end-to-end readiness in MAX. Deployment, catalog/routing availability, provider permissions and mobile/web acceptance require separate verification.
Signed-in users can create a scenario directly in the Mini App by choosing a theme or entering custom text. The app saves an owner draft before opening route conditions and start/finish selection. Calculation requires explicit confirmation. A new scenario is also available from the route library. Bot messages are an additional entry point.
